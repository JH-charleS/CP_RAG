# CP_RAG 项目文档（面试版）

## 1. 详细项目介绍

### 1.1 项目背景

在算法学习场景中，用户提问具有明显分层特征：

- 一部分是**题号明确**的问题（如 `LeetCode 1`、`P1000`），期望直接命中已有题解；
- 一部分是**通用算法问题**（如“动态规划状态转移怎么设计”），需要语义检索补充知识；
- 一部分是**重复问题**，若每次都走全链路调用大模型，成本高、延迟大。

因此本项目实现了一个分层查询系统：`CP_RAG`（Competitive Programming Retrieval-Augmented Generation）。

### 1.2 项目目标

1. 构建可实际运行的算法问答后端服务；
2. 将“缓存 + 精确检索 + 语义检索 + 大模型生成”统一编排；
3. 在多轮对话中管理学习上下文，避免用户尚未完成当前题目就切换问题；
4. 提供可展示、可演示、可扩展的工程化项目样例。

### 1.3 技术栈与组件

- **后端框架**：FastAPI（异步）
- **配置管理**：Pydantic Settings（`.env`）
- **结构化数据**：MySQL（题解元数据与正文）
- **向量检索**：Milvus（语义检索）
- **缓存与会话状态**：Redis
- **Embedding 模型**：`BAAI/bge-m3`（本地 sentence-transformers）
- **LLM 调用**：OpenAI-compatible API（可对接 DeepSeek）
- **文档解析入库**：`txt/doc/docx/ppt/pptx/pdf`（文本优先 + OCR回退）

### 1.4 核心能力概览

- Tier 1：语义缓存命中（相似度阈值拦截）
- Tier 2：题号识别 + MySQL 精确命中
- Tier 3：Milvus Top-K 语义检索
- Prompt 组装：苏格拉底助教风格（引导式教学）
- 会话管理：`session_id`、历史消息、当前题目锁定与完成判定
- 前端演示页：可发送问题、结束当前问题、切换会话

## 2. 项目实现流程（业务视角）

下面流程按“真实用户请求”的业务路径描述：

### 2.1 请求进入网关/API

用户在前端输入问题，调用 `POST /api/v1/query`，携带：

- `query`：用户问题
- `session_id`：会话标识
- `finish_current`：是否确认结束当前题

### 2.2 会话策略判断（防误切题）

服务先读取 Redis 中该会话的 `active_problem_id`：

- 如果用户未确认完成当前题，但请求中识别到新的题号且与当前题不同，则返回提示，要求先完成当前题；
- 若显式传 `finish_current=true` 或文本语义判断为“已完成”，则清理当前题锁定，允许进入新题流程。

这个设计贴近教育业务中的“学习路径约束”。

### 2.3 Tier 1：缓存拦截（降本增速）

1. 用 BGE-M3 对 query 向量化；
2. 与 Redis 存储的历史 query 向量做余弦相似度；
3. 若相似度超过阈值（默认 0.95），直接返回缓存答案。

价值：减少重复调用 LLM，显著降低时延和 token 成本。

### 2.4 Tier 2：题号精确检索（高精度）

如果缓存未命中：

1. 先做题号抽取（LeetCode / 洛谷 / Codeforces / AtCoder 等）；
2. 命中题号后查询 MySQL `solutions`；
3. 读取结构化题解上下文与代码片段。

价值：对于“明确题号”的请求，召回准确率高、结果稳定。

### 2.5 Tier 3：语义检索（补充泛化能力）

并行/后续执行语义检索：

1. 使用同一 embedding 对 query 向量化；
2. 在 Milvus collection 中按向量相似度检索 Top-K；
3. 拼接命中文档片段作为 RAG 上下文。

价值：覆盖“没有明确题号”的通用问题，提高回答信息密度。

### 2.6 Prompt 组装与 LLM 生成

服务将以下信息统一拼装到 payload：

- 系统提示词（苏格拉底助教风格）
- 用户当前问题
- Tier2 精确检索上下文
- Tier3 语义检索上下文
- 会话历史（最近多轮）

然后调用 OpenAI-compatible LLM API，得到最终回答。

### 2.7 回写与闭环

回答返回用户前后，系统异步回写：

- Redis 缓存：`query_vector + answer`
- 会话历史：`user/assistant`
- 会话状态：`active_problem_id`

形成“请求—检索—生成—沉淀”的闭环。

## 3. 项目成果与总结

### 3.1 交付成果

1. **完整后端服务**：FastAPI + 多数据源异步连接管理；
2. **三层路由架构**：缓存、精确检索、语义检索协同；
3. **对话能力增强**：会话历史与问题完成判定；
4. **可运行前端页面**：用于演示完整问答链路；
5. **文档入库脚本**：支持多种原始文档格式解析后写入 Milvus；
6. **一键/本地启动**：`start.bat` 与 `app_run.py`。

### 3.2 工程收益

- **可维护性**：配置集中化、模块边界清晰（API / Core / DB / Utils）；
- **可扩展性**：便于新增题源平台、替换模型、调整检索策略；
- **可观测性基础**：health 检查、响应元信息（缓存命中、命中题号、rag_hits）；
- **面试展示价值**：覆盖 LLM 工程常见关键点（RAG、缓存、会话、服务化、数据管道）。

### 3.3 可继续优化方向

- 引入 reranker 提升检索排序质量；
- 增加离线评测集与自动化指标（命中率、回答质量、延迟、成本）；
- 强化生产级监控（trace、慢请求、token消耗）；
- 对 OCR 流程做批处理限流与资源隔离。

## 4. 面试可能会被问到的问题与答案

### Q1：为什么做三层（缓存/精确/语义）而不是只做 RAG？
**A：**不同问题类型对应不同最优路径。缓存适合重复请求降本增速；精确检索对题号问题准确且稳定；语义检索覆盖泛化问题。三层结合兼顾性能、准确性和覆盖率。

### Q2：如何判断是否命中缓存？
**A：**对 query 做向量化，与历史 query 向量计算余弦相似度；超过阈值（默认 0.95）即命中。阈值可配置，并可按业务调优。

### Q3：如果用户没给题号，系统如何工作？
**A：**Tier2 可能不命中，此时依赖 Tier3 的 Milvus 语义检索结果，拼接上下文后交给 LLM 生成回答。

### Q4：为什么要做“当前题完成判定”？
**A：**教育场景下用户频繁跳题会破坏学习闭环。通过会话状态与完成判定，能保持对话连续性与教学节奏。

### Q5：会话状态是怎么存的？
**A：**Redis 按 `session_id` 维护 `active_problem_id` 与历史消息列表。这样无状态 API 实例也能共享会话状态，便于横向扩展。

### Q6：Milvus 字段不一致时如何处理？
**A：**代码做了字段兼容策略（如 `context`/`content`、`id`/`doc_id`），并通过 `.env` 配置输出字段，避免硬编码耦合。

### Q7：为什么 embedding 用本地模型？
**A：**本地 embedding 可以降低外部依赖和调用成本，同时保证向量一致性；尤其在批量入库阶段更可控。

### Q8：怎么控制成本与时延？
**A：**
1. 先走缓存；
2. 只在必要时调用 LLM；
3. Top-K 适度压缩（当前 2）；
4. 异步回写，避免阻塞主链路。

### Q9：这个项目最像真实业务的点是什么？
**A：**不是单纯“调用一个模型”，而是实现了完整业务链路：数据入库、检索编排、策略控制、会话管理、服务化接口和可演示前端。

### Q10：如果要上生产，你会优先补什么？
**A：**优先补评测与监控：离线评测集、在线埋点、错误分类、重试与熔断机制；其次是权限与多租户隔离。

## 附：3分钟口述版（面试可直接说）

我做的项目叫 **CP_RAG**，是一个面向算法题学习场景的多层检索问答系统。核心目标不是“单次回答”，而是把 **检索准确性、响应速度、教学引导和会话连续性** 结合起来。

先说业务痛点：  
用户提问分三类——第一类是有题号的，比如 `LeetCode 1`；第二类是通用算法问题，比如“动态规划状态转移怎么设计”；第三类是重复提问。如果全都直接调大模型，成本高、延迟高，而且学习过程不连贯。

所以我设计了三层路由：

第一层是 **语义缓存**。  
我先把 query 向量化，然后跟 Redis 里历史问题向量做余弦相似度对比，超过阈值就直接返回缓存答案，显著降低重复请求的延迟和 token 成本。

第二层是 **题号精确检索**。  
我用正则识别主流平台题号，比如 LeetCode、洛谷、Codeforces，然后去 MySQL 的 `solutions` 表做精确命中，拿到结构化题解和代码，这一层对明确题号问题准确率很高。

第三层是 **Milvus 语义检索**。  
对于没有题号或题号信息不足的场景，我用本地 BGE-M3 做 embedding，在 Milvus 做 Top-K 检索，把相关文档片段拼接进上下文，再交给 LLM 生成回答。

在对话层面，我还做了 **会话状态控制**：  
每个 `session_id` 都有当前题目状态。如果用户还没完成当前题就想切题，系统会先拦截并提示确认完成，避免学习过程被打断。用户可以显式结束当前题，或者通过语义完成度判断解锁下一题。

工程实现上，我用 FastAPI 做异步服务，Redis/MySQL/Milvus 都是单例连接管理；Embedding 用本地模型，LLM 走 OpenAI-compatible 接口（可接 DeepSeek）；前端有一个轻量页面可以直接演示完整链路。  
另外我补了文档入库脚本，支持多格式文档解析并写入 Milvus。

最终效果是：  
- 有题号时能高精度命中；  
- 无题号时有语义检索兜底；  
- 重复问题走缓存快速返回；  
- 多轮学习过程中能保持上下文和节奏。  

这个项目对我来说最大的价值，是把 LLM 工程里最核心的几个模块——**RAG、缓存、会话状态、服务化与数据管道**——串成了可运行、可演示、可扩展的一体化方案。
